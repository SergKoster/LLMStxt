# Архитектура (предполагаемая)

Этап 1 — ровно по `docs/TASK.md`. Этап 2 — `llms-full.txt` и выбор файлов галочками (раздел
«Этапы»). Этап 3 — анализ сайта перед генерацией (раздел «Этап 3»). Всё сделано.

## Структура проекта

```
llms/
├── app/
│   ├── main.py          # FastAPI: маршруты, раздача статики, запуск уборки при старте
│   ├── config.py        # все числа и пути в одном месте (таймаут, глубина, папка, срок хранения)
│   ├── validation.py    # проверка URL
│   ├── tasks.py         # хранилище задач в памяти + фоновая функция
│   ├── generator.py     # обёртка над командой llms-gen (subprocess)
│   ├── probe.py         # проверочные запросы: схема https/http и причина неудачного обхода
│   ├── analysis.py      # анализ сайта перед генерацией: запросы, рекомендации файлов, советы
│   ├── site_checks.py   # проверки по уже скачанным ответам (в сеть не ходит)
│   ├── cleanup.py       # удаление файлов старше 1 часа
│   └── static/
│       ├── index.html
│       ├── app.js
│       └── style.css
├── tests/               # pytest: валидация URL, статусы, уборка (llms-gen подменяется)
├── docs/
├── Dockerfile           # python:3.11-slim, без Chromium
├── docker-compose.yml
├── requirements.txt     # fastapi, uvicorn, llms-generator==<версия>
└── README.md
```

## Как идёт запрос

1. Браузер открывает `/` → `index.html`.
1а. (Этап 3) JS шлёт `POST /analyze {url}` → сервер сразу отвечает отчётом: советы по сайту и
   список файлов с пометкой «рекомендуем». Пользователь выбирает файлы галочками.
2. JS шлёт `POST /generate {url, files}` — `url` уже со схемой, которую выбрал анализ.
3. Сервер: проверка URL → `task_id = uuid4()` → запись задачи со статусом `processing` →
   `BackgroundTasks.add_task(...)` → ответ `{task_id, status: "processing"}`.
4. Фоновая функция запускает `llms-gen`, ждёт до 180 секунд, пишет файл или текст ошибки.
5. JS каждые 3 секунды делает `GET /status/{task_id}`:
   - ответ JSON `processing` → ждать дальше;
   - ответ JSON `error` → показать текст ошибки;
   - ответ не JSON → это файл, сохранить его как `llms.txt`.

## API

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/` | страница |
| POST | `/analyze` | `200 {status: "done", url, files, advice, instruction}` · `422 {status: "error", error}` · `429` занято |
| POST | `/generate` | `200 {task_id, status: "processing"}` · `422 {detail}` при плохом URL |
| GET | `/status/{task_id}` | файл · `{status: "processing"}` · `{status: "error", error}` · `404` для неизвестного id |

## Решения по модулям

**main.py** — страница `/`: к ссылкам на `app.js` и `style.css` при старте дописывается отпечаток
их содержимого (`?v=…`), страница отдаётся с `Cache-Control: no-cache`. Так после обновления
браузер не возьмёт старый скрипт из кэша.

**validation.py**
- Схема только `http`/`https`, есть хост, длина до ~2000 символов. Адрес без схемы получает
  `https://`, а реальную схему выбирает `probe.pick_scheme` в фоновой задаче (решение 2026-11-11).
- Хост должен резолвиться в DNS — иначе сразу понятная ошибка «сайт не найден».
- Запрет локальных и внутренних адресов (`localhost`, `127.0.0.0/8`, `10/8`, `192.168/16` и т.п.),
  чтобы через сервис нельзя было ходить во внутреннюю сеть сервера.

**tasks.py**
- Задачи — словарь в памяти: `task_id → {status, error, created_at}`. Базы нет.
- Следствие: uvicorn запускается **в один процесс** (`--workers 1`); после перезапуска контейнера
  незавершённые задачи теряются. Для MVP это нормально.
- Ограничение числа одновременных генераций (семафор), чтобы сервер не легли от десятка запросов.

**generator.py**
- `subprocess.run([...], timeout=180, capture_output=True)`, без `shell=True`.
- Команда: `llms-gen <url> --depth 3 --output <путь> --no-js --max-pages N --delay D`.
  - `--no-js` — без Playwright/Chromium, образ остаётся лёгким.
  - `--max-pages` и `--delay` **в задании нет, но без них критерий «habr.com за минуту» не выполнить**:
    у `llms-gen` пауза по умолчанию 1 с на запрос и нет лимита страниц. Точные числа подобрать
    при реализации на реальных сайтах.
- Файл пишется во временное имя и переименовывается, когда готов, — чтобы `/status` не отдал половину.
- Ошибки переводятся в понятный текст: таймаут, сайт не отвечает, пустой результат, код возврата ≠ 0.

**probe.py** (2026-11-11)
- `pick_scheme`: если схему подставили мы — запрос по `https://`; любой HTTP-ответ (даже 403) значит
  «открылся». Нет ответа — пробуем `http://`. Нет и его — ошибка «ни по https://, ни по http://».
- `diagnose`: вызывается **только** когда `llms-gen` написал `No pages found`. Один запрос к стартовой
  странице с тем же User-Agent, что у `llms-gen`, и по ответу — готовый текст (401, 403/429, 404, 5xx,
  нет ответа, не HTML, robots.txt запрещает, пустая страница). Причина не ясна — общий текст.
- Пользователю показываются только тексты из `probe.py`, ответ сайта и вывод `llms-gen` — никогда.
- Редиректы проверяются: только `http`/`https` и только на публичные адреса (`check_public_host`).

**cleanup.py**
- Фоновый цикл при старте приложения: раз в несколько минут удаляет файлы в `/tmp/llms_outputs`
  старше 1 часа и записи задач из словаря.

**static/**
- Один экран: поле, кнопка, индикатор, блок ошибки. Тексты и внешний вид — по решению владельца.

## Docker

- `Dockerfile`: `python:3.11-slim` → `pip install -r requirements.txt` → `uvicorn app.main:app`.
- `docker-compose.yml`: один сервис, порт `8000:8000`, `restart: unless-stopped`.

## Этапы

**Этап 1 — MVP по заданию.** Всё из `docs/TASK.md`, плюс `README.md`. Проверка: критерии приёмки.

**Этап 2 — `llms-full.txt` (сделан 2026-11-10).** Из дополнений владелец оставил только его;
аудит и проверку файла не делаем. Справка по остальным — в `docs/RESEARCH.md`.

Как устроено:

- **Выбор файлов.** `POST /generate` принимает необязательное поле `files` — список из
  `"llms.txt"` и `"llms-full.txt"`. Без поля — только `llms.txt`, как в задании. Пустой список
  или незнакомое имя — `422`.
- **Генерация.** `llms-gen` получает флаг `--full` и за тот же обход пишет оба файла. Имя второго
  файла у него жёсткое (`llms-full.txt` рядом с основным), поэтому каждая задача работает в своей
  папке `OUTPUT_DIR/{task_id}.work/` — иначе параллельные задачи затирали бы файлы друг друга.
  Папка удаляется сразу после задачи.
- **Результат — всегда один файл** в `OUTPUT_DIR`, по имени видно, что внутри:
  `{task_id}.txt` → `llms.txt`, `{task_id}.full.txt` → `llms-full.txt`,
  `{task_id}.zip` → `llms.zip` с обоими файлами. Один выбранный файл отдаётся как есть,
  больше одного — архивом.
- **`GET /status/{task_id}`** не изменился: отдаёт готовый файл (или архив) с нужным именем в
  `Content-Disposition`.
- **Страница.** Список с галочками под полем; у выбранных файлов подпись «генерируется» /
  «сгенерирован»; в конце «Ваш файл готов» или «Ваш архив готов» и кнопка «Скачать».
  Библиотека пишет оба файла одновременно в самом конце обхода, поэтому подписи у файлов
  меняются вместе.
- **Чтобы добавить ещё один файл:** имя в `AVAILABLE_FILES` и пояснение в `FILE_ABOUT`
  (`config.py`), генерация в `generator.py`, суффикс в `_RESULTS` (`tasks.py`), правило
  рекомендации в `analysis.offer_files`. Строку с галочкой страница рисует сама по ответу анализа.

## Этап 3 — анализ сайта (2026-11-12)

`POST /analyze` — обычный синхронный запрос (не фоновая задача): анализ занимает 1–3 секунды.
FastAPI выполняет его в отдельном потоке. Одновременно — не больше `MAX_CONCURRENT_ANALYSES`,
дальше `429`.

Порядок в `analysis.py`:
1. Схема (`probe.pick_scheme`, если пользователь её не написал) и главная страница. Главная не
   открылась, ответила ошибкой или это не HTML — анализ останавливается с готовым текстом
   (тексты из `probe.py`, плюс «неправильный сертификат» и «не удалось открыть главную»).
2. Параллельно, не больше `ANALYSIS_PARALLEL_REQUESTS` запросов сразу: `/llms.txt`,
   `/llms-full.txt`, `/robots.txt`, случайный несуществующий адрес, `https://` (если сайт открылся
   по http) и до 9 ссылок с главной на этот же сайт (`ANALYSIS_MAX_PAGES` = 10 вместе с главной).
   Все запросы — через `probe.fetch`: публичные адреса, проверка редиректов, 256 КБ на ответ.
3. Разбор — в `site_checks.py`, он в сеть не ходит.

**Рекомендации файлов** (`analysis.offer_files`):

| На сайте | `llms.txt` | `llms-full.txt` |
|---|---|---|
| файла нет (или вместо файла отдаётся HTML-страница) | рекомендуем | рекомендуем |
| файл есть и по стандарту | не рекомендуем, но можно выбрать | — |
| файл есть, но не по стандарту | рекомендуем, «сделан не по стандарту» | — |
| файл есть | — | не рекомендуем, но можно выбрать |

«По стандарту» (`site_checks.llms_txt_is_standard`) — правило смягчено по решению владельца
(2026-11-12), проверяется только основа: UTF-8; первая строка `# `, такой заголовок один (строки
внутри блоков кода ``` не считаются); пункт, который начинается со ссылки (`- [`), начинается с
правильной ссылки `- [текст](http(s)://…)`. Подзаголовки `###`, пункты без ссылки, повторы ссылок
и описание через « - » вместо «:» разрешены. Файл больше 256 КБ читается не целиком, обрезанная
последняя строка отбрасывается.

**Советы по сайту** (`site_checks.check_*`, проверки 1, 2, 5, 6, 7, 8 из `docs/RESEARCH.md`, раздел 4).
Совет появляется только при найденной проблеме. Чтобы не было мелочей:
- «пустая без скриптов» — видимого текста нет совсем или меньше 200 символов, и при этом есть
  контейнер JS-приложения (`id="root"`, `app`, `__next`, `__nuxt`…). То же правило использует
  `probe` для ошибки «текста на страницах нет»;
- «битые страницы» — только 404/410/5xx (403 часто ставит защита от ботов, это не поломка);
- заголовок/описание — только если проблема на главной или хотя бы на половине страниц;
  одна и та же страница по двум адресам (`/` и `/index.html`) в счёт не идёт.

**Чтобы добавить новую проверку:** функция `check_…` в `site_checks.py` (на вход — уже скачанное,
на выход — `Advice` или `None`), её вызов в списке `advice` в `analysis._analyze`, если нужен
новый запрос — добавить его в пул там же; тесты — в `tests/test_site_checks.py`.

**Пояснения к файлам** — `config.FILE_ABOUT`. На странице это кнопка «?» с подсказкой у галочки,
в архиве — файл `config.INSTRUCTION_NAME` с теми же текстами (`tasks.instruction_text`).

## Что выяснилось при реализации (2026-11-10)

- **`llms-gen` соблюдает `Crawl-delay` из robots.txt сайта**, а файл пишет только в конце обхода.
  У habr.com пауза 10 секунд: 30 страниц шли 5 минут 19 секунд. Поэтому `generator.py` сам читает
  `Crawl-delay` и заранее считает `--max-pages` так, чтобы обход занял около минуты
  (`CRAWL_TIME_BUDGET_SECONDS`). Итог: habr.com — 5 страниц за 68 секунд, priisk.pro — 7 секунд.
- **`llms-gen` 0.3.2 ломает пункты списка**, если в заголовке или описании страницы есть перенос
  строки, — файл выходит невалидным. `fix_broken_entries()` в `generator.py` склеивает их обратно.
- Несуществующий сайт: `llms-gen` возвращает код 1 и `ERROR: No pages found`. До него дело обычно
  не доходит — адрес отсекает проверка DNS в `validation.py`.
- Страница: только поле, кнопка, индикатор и текст ошибки (решение владельца — ничего лишнего).
  Когда файл готов, появляются текст «Ваш файл готов» и кнопка «Скачать»; сам файл не скачивается.

- **Docker проверен** (2026-11-10): `docker compose up --build` собирает и запускает контейнер,
  в нём priisk.pro — 3 секунды, habr.com — 56 секунд (5 ссылок), оба файла проходят валидатор,
  несуществующий сайт даёт 422 с понятным текстом. Сервис в контейнере работает не от root.
- Для агентов: Docker Desktop нельзя запускать напрямую из приложения Claude на Windows — оно
  работает в песочнице, и Docker падает с ошибкой про `dockerInference`. Запускать через
  Проводник: `explorer.exe "<путь>\Docker Desktop.exe"`.

## Что пока не проверено

- Защита от внутренних адресов проверяет только введённый хост. Если внешний сайт перенаправит
  на внутренний адрес, `llms-gen` пойдёт по редиректу.
