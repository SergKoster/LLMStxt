# llms — генератор llms.txt по URL сайта

Веб-сервис: пользователь вводит URL своего сайта, сервис в фоне обходит сайт и отдаёт на скачивание
`llms.txt`. Позже — другие полезные файлы для сайта (см. `docs/RESEARCH.md`, раздел «Дополнения»).
Проект маленький, главное — чтобы работал.

## Документы

## Стек (строго по заданию)

- Python 3.11+, FastAPI, фоновые задачи через `BackgroundTasks`.
- Фронт: HTML + ванильный JS, без фреймворков и сборщиков.
- Генерация: библиотека `llms-generator` (команда `llms-gen`), вызывается через `subprocess`.
- Docker, запуск одной командой `docker-compose up`.

Не добавлять: Celery, Redis, базы данных, React/Vue, платные API и ключи LLM.

## Правила

- Требования из `docs/TASK.md` не менять и не «улучшать» молча. Не согласен — скажи.
- Дополнения сверх задания (этап 2) делаются только после «да» от владельца проекта.
- Тексты интерфейса, внешний вид, числа лимитов сверх задания — решает владелец, не агент.
- URL от пользователя передавать в `subprocess` только списком аргументов, без `shell=True`.
- Версию `llms-generator` держать зафиксированной в `requirements.txt`.
- Общаться и писать доки по-русски.

## Команды

Появятся после этапа 1. Запуск: `docker-compose up --build`, сервис на `http://localhost:8000`.

## Решения владельца (2026-11-10)

- Порядок: сначала этап 1 строго по заданию, дополнения — потом.
- Дополнения на этап 2 (первый вариант, позже сужен — см. ниже): `llms-full.txt`, отчёт-аудит
  сайта, проверка готового `llms.txt`. Смысл дополнений — пара готовых файлов, которые можно быстро закинуть на свой сайт.
- `robots.txt` для ИИ-ботов **пока не делаем**.
- Архитектуру дополнений продумать отдельно перед этапом 2, заранее под них ничего не строить.
- Интерфейс на русском; внешний вид — простой минимальный, на усмотрение агента.
- **НА СТРАНИЦЕ НИЧЕГО ЛИШНЕГО.** Ни одного блока, подписи, заголовка, подсказки или
  пояснительного текста, о которых владелец прямо не просил. Сейчас на странице только то, что
  требует задание: поле URL, кнопка «Сгенерировать», индикатор загрузки, текст ошибки, —
  плюс по просьбе владельца: когда файл готов, текст «Ваш файл готов» и кнопка «Скачать»
  (файл сам не скачивается, только по кнопке).
  Любой новый элемент — только после прямой просьбы.
- Этап 2 (решение от 2026-11-10): из дополнений делаем **только `llms-full.txt`**. Аудит и
  проверку файла не делаем. На странице: перед генерацией список с галочками, что генерировать;
  у выбранных файлов подпись «генерируется» / «сгенерирован»; один файл отдаётся как есть,
  больше одного — zip-архивом.
- Проект делается для сайта https://priisk.pro/ («прИИск», одностраничник). Это главный тестовый
  сайт; цвета страницы взяты с него (зелёный `#1e6f5c`).

## Решения владельца (2026-11-11)

- Адрес без схемы: сервис сам подставляет сначала `https://`, если не открылся — `http://`.
- Конкретная причина ошибки: свой проверочный запрос к сайту — **только когда обход не удался**.
- Тексты ошибок — деловым, но человеческим языком, понятное объяснение (черновик в `docs/TASKS.md`).
- Антибот-защиту сайтов (как у dodopizza.ru) не обходим.

## Решения владельца (2026-11-12)

- Сервис должен быть понятен человеку, который не разбирается в теме: каждый файл, который
  пользователь получает, даётся с пояснением, зачем он нужен и что с ним делать.
- Новый порядок: сначала анализ сайта, потом список предлагаемых файлов. Рекомендованные
  помечены; файл, который на сайте уже есть по стандарту (например, `llms.txt`), не рекомендуется,
  но выбрать его всё равно можно. Это отменяет прежнее «аудит не делаем» в части анализа перед
  генерацией. Подробности и открытые вопросы — `docs/TASKS.md`, этап 3.
- Пояснения и пометки рекомендаций — прямая просьба владельца, правило «ничего лишнего» к ним
  не мешает. Сами тексты утверждает владелец.
- MCP-сервер — в «На будущее» (`docs/TASKS.md`), пока не делаем.
- Ответы по этапу 3 (подробно — `docs/TASKS.md`): `llms.txt` «уже есть» = есть и по стандарту;
  не по стандарту — фраза «У вас уже есть llms.txt, но он сделан не по стандарту», без списка
  ошибок; `llms-full.txt` рекомендуем, если его нет; пояснение — кнопка с подсказкой у галочки;
  в zip — файл-инструкция, и на странице сказано, в каком он файле; процесс не поясняем.
- Анализ показывает не только файлы, но и советы по сайту — явные недоделки, видимые без
  нейросети. Без кучи мелких советов: совет только если проблема найдена. Берём проверки
  1, 2, 5, 6, 7, 8 из `docs/RESEARCH.md`, раздел 4; ИИ-боты в `robots.txt` и защиту хостинга
  (3, 4) и проверки «в запасе» не берём. Задачи — `docs/TASKS.md`, раздел 3.3.
- Анализ смотрит главную и ссылки с неё на этот же сайт (не больше 10 страниц). Отчёт со
  советами — над списком файлов, сворачивается целиком, при появлении развёрнут; у совета короткая строка, а «что
  сделать» разворачивается по нажатию (не всплывающая подсказка).

- Правки после теста (2026-11-12): вверху страницы заголовок «Генератор» (заглушка, название
  ещё будет), под ним «Проверка вашего сайта на недоработки», перед полем подпись «Введите URL
  своего сайта:», в поле подсказка-плейсхолдер. Пояснения к файлам — проще: главное, что файл
  нужен ИИ-агентам, которые ищут информацию в интернете; часть «куда положить» оставить.
- Совет 6 «не настроен для телефонов» пока не показываем (ложные срабатывания у сайтов с
  отдельной страницей для телефонов). Сейчас в анализе проверки 1, 2, 5, 7, 8.

## Как раскладывать задачи

- Каждое новое нововведение до начала работы разложить в `docs/TASKS.md` на небольшие подшаги
  с номерами (3.1.1, 3.1.2…): что сделать, в каком файле, как проверить.
- Порядок — по зависимостям: сначала то, без чего не сделать остальное. Подшаг должен быть
  проверяемым сам по себе (тест или проверка в браузере).
- Решения, которые принимает владелец (тексты, внешний вид, правила, числа), — отдельным пунктом
  «Решения владельца» перед зависящими от них подшагами, вопросы — списком в том же разделе.
- Идеи из раздела «На будущее» на подшаги не раскладывать, пока владелец не решит их делать.
